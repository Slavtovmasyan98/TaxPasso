Режим по умолчанию: `dry_run_only=true`, `repair_history=false`, `confirm=CHECK`.
При старой истории он остановится с указанием отдельного режима REPAIR; никаких записей в БД не делает.
После нормализации истории CHECK выводит план без применения миграций.

Workflow запускается из main, но SQL берёт из неизменяемого коммита кандидата: иначе до слияния PR #11 нужных миграций в main нет.
Проверяются неизменность файлов 001–010 относительно main, полный набор 001–015, адрес production и допустимая история.
Успешная проверка журнала после применения подтверждает версии; она не заменяет сверку схемы и проверку сайтов.

## Что сохраняет снимок

Workflow использует `pg_dump` той же основной версии PostgreSQL, что сервер, без исключения схем; при недостатке прав останавливается.
Архив содержит схему, данные и журнал миграций. Перед загрузкой проверяются оглавление архива и расшифровка с совпадением SHA-256.
В GitHub Artifacts загружается только `production.dump.gpg`; незашифрованный архив удаляется в `finally`.
Ошибки создания, шифрования или загрузки снимка блокируют и REPAIR, и APPLY.

Это логический снимок базы, а не полная копия проекта Supabase. В нём нет байтов файлов Storage, кластерных ролей/их паролей и настроек платформы. Права объектов исключены (`--no-acl`), владельцы при восстановлении требуют согласования. Перед production нужно проверить восстановление на изолированной базе; проверка оглавления не доказывает восстановимость.
Скачайте артефакт и сохраните отдельно. Для расшифровки: `gpg --output production.dump --decrypt production.dump.gpg` (пароль вводится интерактивно). Не восстанавливайте снимок поверх рабочей базы без отдельного плана восстановления.

`migration repair` меняет журнал; обратная перестановка версий сама по себе не гарантирует восстановления исходных столбцов `name` и `statements`. Снимок сохраняет исходные записи.
`dry_run_only=true` вместе с `repair_history=true` выполняет запись в журнал и требует `confirm=REPAIR`; это не режим без изменений.
