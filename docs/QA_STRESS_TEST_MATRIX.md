## Как проверяли

Не по чтению кода, а **исполнением на живой схеме**: пробы через SQL с правами реальных ролей (`authenticated` + JWT клиента / админа / партнёра), каждая в транзакции с обязательным откатом. Базовое состояние — **staging, миграции 011–018 из репозитория** (то же самое сейчас в production).

Статусы: **PASS** — проверено, работает · **FAIL** — подтверждённая дыра (получила ID F-xx и todo-тест в `qa_stress.test.mjs`) · **NV** — из базы проверить нельзя (UI, сеть, реальная параллельность, внешние сервисы).

Приоритеты: **P0** потеря денег / утечка данных / повышение прав · **P1** неверное состояние или застрявший заказ · **P2** UX и косметика.

**P0, подтверждённых как эксплуатируемые снаружи, нет.** Прямой записи оплаты нет, повышения прав нет, доступа к чужим данным нет, вызова функций без входа нет. Есть один **блокирующий пункт перед запуском продаж** (F-09).

## Коррекции к вводным промпта («Known gaps»)

- «Сервер не валидирует сумму оплаты» — подтверждено, но серьёзнее, чем кажется: **нет даже сохранённой суммы оплаты**, поэтому «возврат больше оплаченного» проверить нечем (F-01 и F-09 решаются вместе).
- «Add-on renewals не автоматизированы» — верно; схема продления есть (`period_number`), публичной функции продления нет.
- «Partners must never see anything about money» — по факту: возвраты, услуги, журнал закрыты полностью; **утекают два канала** — текст `cancel_reason` (F-04) и `in_work` (F-12).
- «MFA gate currently OFF» — включать только после того, как админ **уже** подключил аутентификатор; при aal1 админ видит пустой кабинет без объяснения.

## Что предлагаю сделать (порядок)

1. **Миграция 019 «QA hardening»**: F-01 (возврат только по оплаченному, накопительный лимит), F-02 + F-03 (отмена гасит услуги; триггер не активирует на отменённом), F-04 (убрать `cancel_reason` из `partner_orders`), F-05 (сброс `document_review_proposals`), F-06 (`claim_op` хранит действие+заказ; несовпадение — ошибка), F-07 (`submit_order` для LLC/пакетов вызывает проверку владельцев/долей/ответственного), F-16 (проверка состояния заказа).
2. **Миграция 020 «Payment total»** (F-09): таблица цен продуктов, `order_total()`, оплата принимает сумму и отклоняет несовпадение, сохраняет её. Обязательна до включения хотя бы одной доп. услуги.
3. **Решения владельца:** F-08 (когда партнёр теряет доступ к закрытому/отменённому заказу), F-12 (нужен ли партнёру сигнал «в работе» в текущем виде), F-11 (уникальность черновика).
4. Регресс-тесты R1–R3 положить в CI **сейчас** — они охраняют то, что уже работает.
